# Decisions and known issues

Why Siphon works the way it does, and what is known not to be right yet. What each part does is in [how-it-works.md](how-it-works.md).

## Decisions

### Downloads and quality

- **Copy before convert.** Presets pick a stream the target already plays and re-wrap it. Conversion happens only when the target needs it or the user asks, because converting is slower and never improves quality. What each preset does, and the sources behind it, are in [presets.md](presets.md).
- **Presets are purpose-based** (2026-11-17, replacing ten flat chips): the user picks a group (shown as Max quality, Watch, Audio, Share; a new user starts on Max quality), a target in it, and optionally a quality. The groups, targets and tiers are defined once, in `src-tauri/src/plan/registry.rs`; the frontend reads them through `get_presets` and only maps icon names to icons.
- **Choices fold away** (2026-11-18, replacing rows of pills): under the group tabs, each choice (target, limit, files, format, quality, saved presets) is a facet (`src/components/ui/facet.tsx`) showing only its current value. Pointing at it, or tabbing into it, unfolds it across the whole row over its neighbours, which fade out, so nothing moves or peeks out; it stays open until the pointer or focus leaves; sizes show only for the option pointed at. The plan summary keeps two lines (what, how big, how long) and puts the explanation and info notes behind its ⓘ; warnings stay in view. The aim was less text on screen at once.
- **Decisions come from the video's formats and this machine** (`Capabilities`: working hardware encoders, ffmpeg's `-request_size`, the Windows video extensions installed). The same preset copies on one site and converts on another; tests cover a YouTube-style and an X-style format list.
- **The planner is the single source of truth.** `plan()` in `src-tauri/src/plan/mod.rs` is a pure function from formats, the choice, the trim range and the machine's capabilities to a recipe, including which encoder runs it. The summary shown before downloading and the yt-dlp/ffmpeg commands are both generated from that recipe, so the app cannot describe one thing and do another.
- **Stream ranking** prefers plain files over HLS copies, tracks with known codecs over unknown ones, and audio without levelled ("DRC") volume. These rules came from a real YouTube format list and have regression tests.
- **Upload limits take the cautious side where sources disagree** (see presets.md). Discord Free is 20 MB, confirmed by the owner.
- **Share checks its result.** The finished file is measured against the limit and encoded again at a proportionally lower bitrate if it is over (twice at most, `Recipe::shrunk`); a copied original that came out over is converted with the plan's `fallback`. A video too long to look decent at any size is refused with a suggestion to trim (`ErrorKind::TooLong` if it reaches the download).
- **No Edit group** (removed 2026-11-21, after 0.15, the owner's call). It made files for video editors: H.264 at a constant frame rate with 48 kHz sound and a key frame every second, or ProRes 422 ("Smoothest editing"), with subtitles as an SRT file beside the video. Its four targets (Premiere Pro, DaVinci Resolve, CapCut, Vegas) all made the same file, the owner isn't an editor, and editors convert with their own tools, so it was taking room in the window for nobody. Everything only it used went with it: ProRes, the constant-frame-rate and key-frame settings, resampling the sound, and the SRT file. Customize still makes H.264 in MP4 or MOV, with uncompressed sound if wanted. A `choices.json` that remembers Edit loses only that (`choices::forget_unknown`), not the saved presets with it. A download paused or failed with Edit before the update fails with a raw error on Resume or Try again, since its choice names a target that no longer exists; it can be removed from the list.
- **Android's Best stops at 1080p**; higher is in the quality row. Apple converts to HEVC only with a hardware HEVC encoder, otherwise to H.264 on the GPU, which is far quicker than HEVC on the CPU.
- **The playlist total looks up a sample, not every video** (2026-11-18, `SAMPLE` and `totalSize` in `PlaylistPane.tsx`). A full lookup takes about 3.4 s, three at a time (`estimate_download`), and every video starts selected, so a 182-video playlist kept yt-dlp busy for 3½ minutes and a 1,218-video channel tab for about 23, sending YouTube a request per video, the kind of burst that brings on bot checks. Now the first 15 selected videos are looked up, and the rest are scaled from their size per second of video by the length the playlist listing already gives (or by their average per video where a length is missing); up to 15 selected videos still get an exact total. Measured: the 20-video test playlist came to ≈ 3.4 GB sampled against 3.42 GB with every video looked up; the Blender channel's 1,218 videos were estimated in 17 s. The lookups fill the cache the downloads use.
- **A playlist marks what you already have** (2026-11-18, `useHave` in `PlaylistPane.tsx`), from the download list, the same way as "You already have this": a finished whole-video download whose file is still there is **Downloaded** and starts unselected (it can still be selected to download again); a waiting, running or paused one is **In queue** and can't be selected. Adding videos clears the selection, so pressing the button twice no longer queues everything twice. The file check waits for a look made after the list opened (`isFetchedAfterMount`): reopening a playlist first gets the last answer from the cache, and a file deleted since would otherwise stay unselected.
- **A playlist's folder and numbering travel with each download** (2026-11-18, `Place` in `downloads/mod.rs`), not in Settings, because they belong to one playlist. The frontend keeps them with the download and sends them again on every resume and retry, so a paused video carries on in the same folder. The folder is the playlist's title made safe for Windows (`folder_name`: forbidden characters and control characters become spaces, no dots or spaces at the end, a `_` after reserved names like `CON` or `COM1`, at most 100 characters, so `..\..\Windows` becomes `Windows` inside the download folder). The number goes in front of the user's naming style as `07 - `, with as many digits as the playlist's length needs and at least two. Measured 2026-11-18: `Blender Releases/08 - Blender - Blender 4.1 New Features Official Overview.mp3`.
- **A channel is unpacked into its videos** (2026-11-18, `collect_entries` in `ytdlp/metadata.rs`). For `youtube.com/@name`, yt-dlp lists the channel's tabs (Videos, Live, Shorts) as playlists with their videos inside; Siphon used to show the three tabs as if they were videos, and queuing one failed with "This link is a playlist". Their videos are now listed under the tab's name (`section`), and only the first tab starts selected. Entries that link to another playlist without its videos (a channel's Playlists tab, `is_playlist`) open that playlist when clicked. Live and upcoming streams are left out, and a video listed in two tabs is kept once. The shapes are regression tests, taken from the Blender channel.
- **An HTTP 4xx answer no rule knows is the site turning the request down, not a lost connection** (2026-11-18). yt-dlp reports it as "Unable to download webpage: HTTP Error 418", and the connection rule took any "Unable to download webpage" for a dropped connection, telling the user to check their internet. It now says the site turned the request down, rated Unknown for sign-in.
- **A page with a single file is its own format** (2026-11-18, `parse` in `ytdlp/metadata.rs`). For such a page (audio hosts, many generic pages) `yt-dlp -J` prints no `formats` list: the one format's fields (`url`, `format_id`, `ext`, `audio_ext` …) are on the result itself. Siphon read only `formats`, so a page that played said "no downloadable video or audio". Such a result is now read as its own only format; a playlist's link never is. Its codec is often unnamed (`acodec: null`), so it is labelled "audio" and Max quality says it may not play everywhere, though the file is fine (the one tested was AAC in M4A).
- **Format metadata is cached in the backend** by URL (`src-tauri/src/state.rs`), so the frontend never sends formats back. A download that fails with an "outdated" error looks the video up again on its next try, because the site may have changed what it offers since. The cached copy is replaced, not dropped first, so the open video keeps working if the new lookup fails.

### Size estimates

The plan's size comes first from what the site states and a rule of thumb, at once; where that can only estimate, Siphon measures it on the video in the background (2026-11-22, see below). Measured on 2026-11-17 on this PC (NVIDIA, NVENC), with Siphon's own encoder settings, on a talking-head video (AV1 1080p30, 0.28 Mbit/s) and Big Buck Bunny (VP9 and AV1 4K60, 9–12 Mbit/s):

- **Copies, Share and Music are near-exact**: a copy's size is stated by the site, and a size-targeted encode lands on its bitrate (a Share part estimated at 18.6 MB came out at 17.8 MB).
- **A constant-quality conversion depends on the picture**, so until it is measured it is shown as a range, half to double the likely value (`Recipe::estimate`, `quality_encode_kbps`). Resolution alone predicts nothing: the talking head needed a tenth of Big Buck Bunny's bits per pixel. The source's own bitrate does: scaled to the new size by pixels per second to the power 0.75, the encode lands at about 1.4× (talking head) to 2.7× (busy animation) for H.264 on the GPU, 1.5× for HEVC, 1.3–1.7× for H.264 on the CPU. Sites state an average bitrate, and one part of a video can need twice another: Big Buck Bunny's AV1 stream, stated at 9.0 Mbit/s, needed 38, 47 and 64 Mbit/s in three places as H.264 with a key frame every second (the Edit group's settings, since removed).
- The calibration cases are regression tests (`quality_conversion_estimates_cover_what_test_encodes_measured`). To recalibrate, encode 10–20 s samples with the arguments `ffmpeg::convert_args` builds and compare their bitrate with the source's.
- **What can only be estimated is measured on the video, in the background** (2026-11-22, `crate::sizing`, kept in `plan::sizes`; the owner asked for estimates as close as they can be, without making anyone wait). The rule of thumb's likely value was 7–38% off on three full encodes (Big Buck Bunny 4K to HEVC, a 4K talking head to HEVC, ten minutes of Twitch 1080p60 at the chat's settings), and its range ran from half to double. A trimmed part's size, its share of the whole by length, was off by up to half: a 30 s YouTube part held between 0.56 and 1.65 times its share, the busy scenes taking more. So, once a choice has stayed put for 0.8 s (`useMeasuredSize`), the window asks for a measurement (`measure_size`), and the plan is made again when it has found something:
  - **A trimmed part's bytes** (`sizing/parts.rs`): for a file, where in it the part starts and ends, read by ffprobe from the file's index and the packets there (`-read_intervals`, a few MB); for a segmented stream, the sizes of its segments in the part, asked of the server (`HEAD`), at most 120 of them spread over it and scaled; MPEG-TS segments are counted at 96.7% of their bytes, since a file made from them doesn't keep the format's packaging (0.9667–0.9670 on three Twitch segments; without it, two Twitch clips came out 2.9% and 3.2% over). Twitch states a stream's bitrate but not its size, so a whole Twitch VOD is measured from its segments too: 0.12% from the true total of a three-hour VOD's 1,128 segments, where its bitrate said 0.05% and on another VOD 2.5%.
  - **A smart cut's ends** (`cut_ends` in `sizing/mod.rs`): the frames from the start to the first key frame decoding restarts at (traced, as the cut does: YouTube marks other key frames too) and from the last key frame to the end, encoded with the cut's own edge encoder (`smart_cut::edge_encoder`), against what they were. They are visually lossless, so larger: a 30 s 1080p60 YouTube clip's 4.4 s of ends took 7.5 MB more than they had, half again its size. And a clip in MP4 keeps the padding left where room was reserved for its index (`smart_cut::Index::unused`: 267 KB for a 60 s clip, see Trimming).
  - **A conversion** (`sizing/samples.rs`): 12 stretches of 4 s spread over the part (4 of 3 s on the CPU), encoded exactly as the download will, three at a time; each stretch's encoded bytes against its bytes as the site has them, and that ratio against the part's bytes. The site's stream already holds more bytes where the picture is busier, so the ratio varies far less than the bitrate does: scaling the stretches' bitrate to the length instead came to 954–1,687 MB for a 1,183 MB encode. The result is kept as a multiple of the rule of thumb's likely value, which the same encoder's other choices of the same video go by too, within 0.85–1.2 (the quality row). Drawing chat in, left out of the stretches, added next to nothing: a 2-minute Twitch clip with chat came within 0.7%.
  - **Measured end to end** (dev build, 2026-11-22): a 45 s YouTube 1080p60 clip estimated at 21.6 MB, measured at 45.7 MB in 6 s, came out at 45.9 MB; a 90 s Twitch clip 88.2 MB for 88.4 MB (its file made with the padding since 0.17), a 10-minute one 577.8 MB for 578.6 MB; a 30 s clip of the talking head 14.1 MB for 14.2 MB (22.8% under before); Big Buck Bunny for a TV, 0.5–2.1 GB, measured at 1.13 GB in 19–20 s for 1.19 GB; the talking head for a TV, 232–907 MB, measured at 676 MB for 737 MB; the Twitch clip with chat, 59–178 MB, measured at 121.6 MB for 122.5 MB.
  - **Nothing waits for it.** Download starts at once and ends it (`start_download` stops it); so does another choice or leaving the video, and only one runs at a time (`Sizing::alone`). What it found by then is kept with the video (`VideoInfo::sizes`, carried over when the video is looked up again), and what it didn't finish is tried again when the choice is back. It waits while one of Siphon's own encodes runs (`downloads::encoding_now`), rather than slow it on the same encoder. It keeps to the speed limit, but out of the speed the title bar shows (`Throttle::quiet_flow`): no download is running. It measures nothing for a stream as it airs, a video that needed signing in, a playlist's total, or anything the site states the size of.
  - **YouTube refuses a read now and then** (HTTP 403, seen on the 4K stream of one video twice running, while lookups had slowed to 23 s; the same reads went through by hand and a little later): each read is tried again a second later, and a measurement that still can't finish leaves the range in place. `siphon.log` says what each measurement found, or why it couldn't (`size of …`).
- **A conversion says what size it is heading for** (2026-11-22, `Tracker::heading_for`). ffmpeg's `-progress` reports the bytes it has written (`total_size`) beside the time it has reached; scaled to the whole length, that is the size the file is heading for, shown on its row and under Download from 2% of the way ("≈ 103 MB"). A two-pass encode's first pass writes nothing, so only the second says. Measured on a minute of Big Buck Bunny in 4K converted to HEVC: 81 MB at 6% of the way, then between 101 and 112 MB, for a file of 106.4 MB.

### Download speed

Measured on 2026-11-17 with the 4K test video below, on a connection that downloads a whole YouTube stream at about 52 MiB/s.

- **Trimmed parts are fetched in the request size the site names** (`-request_size` for ffmpeg, from the format's `downloader_options.http_chunk_size`; 10 MB on YouTube). yt-dlp hands a section to ffmpeg, which otherwise asks for the rest of the stream in one request, and YouTube answers that at about twice playback speed: a five-minute 1080p part took 172 s, against 6 s in 10 MB requests, with byte-identical output. Sites that name no size are left alone, because a server that ignores `Range` could misbehave. The option is only passed if the installed ffmpeg knows it (checked once, part of `state::CapabilityCache`): an older ffmpeg stops with "Unrecognized option".
- **Segmented streams download four pieces at once** (`--concurrent-fragments 4`): 23 → 55 MiB/s on a YouTube HLS stream. Eight were no faster, and three downloads at once already means twelve connections to one site.
- **YouTube's plain files are fetched as pieces too** (2026-11-21, `youtube:formats=dashy` in `args::recipe_args`). yt-dlp fetches a YouTube stream on one connection, 10 MB at a time, and one connection to YouTube gets anywhere from a third to all of the line: measured with curl, 15–43 MiB/s on one connection against up to 55 on four. As DASH ("dashy"), the same formats under the same ids are fetched in 10 MB pieces, four at once. Measured on the 680 MB 4K AV1 stream of the test video, three rounds each, alternating: 18, 38 and 40 MiB/s as one file, 46 MiB/s every time as pieces (the lookup included; the line's full speed). In the dev build, a whole download of it (video and audio, through the proxy) took 16 s at 55–60 MiB/s, and a pause at 38% resumed from there into a byte-identical file. A trimmed part is left as it was, because ffmpeg fetches it from the stream's address. Only YouTube reads the option.
- **A YouTube connection now and then stops sending** (seen 2026-11-21 in about one download in five, on the last piece): yt-dlp's request hangs until the connection is reset about 18 s later, and the retry finishes in a moment. It's YouTube's or the network's, not the proxy's (it happened without Siphon too). A shorter `--socket-timeout` would cut the wait, but YouTube also pauses legitimately (see the trimmed parts' 20 s), so it's left at yt-dlp's 20 s.
- **yt-dlp retries five times with a growing pause** (1, 2, 4, 8 and 8 s) instead of its default ten in a row with none, which is over within a second. A short outage is ridden out inside one try; a longer one is left to Siphon's own retries (see Queue and settings). A piece of a segmented stream that can't be fetched fails the try (`--abort-on-unavailable-fragments`) instead of being left out of the file.
- **A download starts from the lookup** (2026-11-21, `ytdlp::saved`). What `yt-dlp -J` printed when the link was pasted is kept with the video, and the download (and its subtitles) is given it with `--load-info-json`, instead of yt-dlp looking the video up all over again: about 2.8 s on YouTube, against about 1 s from the saved lookup, nearly all of it yt-dlp starting (measured 2026-11-21). Stream links run out (YouTube's after a few hours, some sites' sooner), so a lookup is used for 15 minutes (`REUSE_FOR`), and an older one is made again before the download; its JSON is let go at the same age. Every retry looks the video up again (`lookup.refresh` in `run`), as every try did while the download looked it up itself, so a link that ran out costs one retry. yt-dlp writes the cookies it sent into what it prints (`cookies` on the video and every format), so a lookup made with the sign-in holds the account's session in plain text: its copy for the download is written without them (`saved::without_cookies`), and the download gets them from its own cookie file as before. The copy (`lookup.info.json` in the work folder) is deleted however the fetch ends. Found before release, 2026-11-21: a paused or failed signed-in download left the session on disk; checked against a local site that needs a session, the download still sent it, a pause left no cookie in the work or download folder, and the resumed file was byte-identical. Measured in the dev build: the 4K test video started downloading 0.5–1 s after Download instead of 2.6 s, and *Me at the zoo* with English subtitles was finished, track and all, 1.5 s after Download.
- **YouTube's pieces are made by Siphon when it starts from the lookup.** `youtube:formats=dashy` acts only while yt-dlp looks a video up, so a saved lookup has the plain files. For a whole video, `saved::in_pieces` makes the chosen formats into pieces the way yt-dlp's dashy does (10 MB ranges of the format's own link, with YouTube's `range` parameter, the last one ending at the size), compared field by field with dashy's output on 2026-11-21: the format loses `downloader_options` and gets `fragments`, and the protocol becomes `http_dash_segments`. Anything that isn't a YouTube plain file of known size, with the request size YouTube names, is left as it is; a trimmed part is never split. `youtube:formats=dashy` stays for a download without a saved lookup. Measured with the saved lookup: 53–57 MiB/s, as with dashy, and the same files.
- **Why a try failed is written to `siphon.log`** ("try failed …", with yt-dlp's own last error), retried or not: the user only sees the last error, and the reason for a retry was otherwise lost.

### Speed limit

Added 2026-11-17. The code is in `src-tauri/src/throttle`.

- **One limit for all downloads, enforced by a local proxy.** yt-dlp's `--limit-rate` can't do it: it limits one process, is fixed when the process starts, and doesn't reach the ffmpeg that fetches trimmed parts. So every yt-dlp download runs with `--proxy http://127.0.0.1:<port>`, and the proxy paces what comes back. yt-dlp hands the proxy to the ffmpeg it starts (as `http_proxy`), so trimmed parts go through it too. The trim preview's low-resolution copy goes through it as well. Not limited: looking a video up, tool and app updates, and the preview the webview streams itself.
- **Every download goes through the proxy, with or without a limit** (the owner's choice, 2026-11-17). Skipping it when Unlimited would mean a limit set later couldn't reach downloads already running. Measured with the debug build, fetching the same YouTube stream: 28.3 and 38.4 MiB/s with yt-dlp on its own, 31.7 and 41.9 MiB/s through the app. The proxy costs nothing measurable.
- **One listener per download**, bound to `127.0.0.1` (never `0.0.0.0`) on a port Windows assigns. That is how the proxy tells downloads apart; proxy credentials would have depended on how yt-dlp and ffmpeg each send them. The listener (a `throttle::Flow`) belongs to the job's record in `DownloadManager`. Removing the job (`end_job`, the one way out whether it finished, failed, was paused or was cancelled) closes the listener and every connection on it. Closing the app also closes the listener of any job that hasn't ended by the end of its grace period. A paused download keeps its files but not its listener; resuming opens a new one. The tests in `downloads::proxy_tests` and `throttle::tests` cover each of these.
- **Fair by download, not by connection.** yt-dlp fetches a segmented stream on four connections, so sharing per connection would give it four shares. The limiter hands tokens to the waiting download that has been given the fewest bytes. A download that wants less than its share leaves the rest to the others, and one that was idle gets no catch-up burst when it starts again. The bucket holds a twentieth of a second at the limit (at least 16 KiB), and reads are 16 KiB while a limit is set (64 KiB without).
- **Only what comes back is limited.** Requests going out are small.
- **The system proxy is still used.** Before, yt-dlp found it itself, the way Python does. The proxy now does the same for each connection: the `HTTP(S)_PROXY`/`ALL_PROXY`/`NO_PROXY` variables if any are set, otherwise Windows' proxy settings (`ProxyServer`, with `ProxyOverride` exceptions). `NO_PROXY` is removed from yt-dlp's environment, because ffmpeg would otherwise go around Siphon's proxy for those sites; the proxy applies it itself.
- **SOCKS proxies are chained to as well** (2026-11-19, `throttle/socks.rs`). From 0.8 to 0.12 only an HTTP proxy was: with a SOCKS proxy in `ALL_PROXY` or Windows' settings (as VPN and privacy tools set), downloads quietly went straight to the site, though yt-dlp had used the proxy before 0.8. Siphon now speaks SOCKS4, 4a and 5 itself, with the names yt-dlp and curl use: `socks5://` and `socks4://` look the site's name up on this PC, `socks5h://` and `socks4a://` let the proxy do it, so the name never reaches this PC's DNS. A bare `socks://`, and Windows' `socks=` entry, are SOCKS4, which is Windows' and Python's default; as in Python, the `socks=` entry serves links whose kind has no entry of its own. A user name and password in the link are percent-decoded (as Python does, now for HTTP proxies too) and sent with SOCKS5's own sign-in (RFC 1929), or as SOCKS4's user ID. A SOCKS proxy that can't be reached or refuses fails the connection with its reason ("the SOCKS proxy can't reach the site"); it never falls back to going direct. The update checks (tools and Siphon itself, through reqwest) failed with a SOCKS proxy in `ALL_PROXY` too, because reqwest was built without its `socks` feature and spoke HTTP to the SOCKS port; it has it now. Measured 2026-11-19 with the dev build and a separate SOCKS5 server (pproxy) in `ALL_PROXY` as `socks5h://`: a whole video and a trimmed part (fetched by ffmpeg) downloaded, every connection to `googlevideo.com` went through the server by name, and the app and tool update checks reached GitHub through it. With the server stopped, a download failed after its retries ("Couldn't reach the site"), with Siphon's proxy refusing each try, and wrote no file.
- **The update checks follow the same proxy as downloads** (2026-11-19, `throttle::follow_system_proxy`). The tool checks and installs and Siphon's own update (through the updater plugin's `configure_client`) ask `upstream::for_host` for each request, instead of reqwest reading the proxy itself. reqwest did read Windows' setting (`tauri-plugin-updater` turns on its `system-proxy` feature, and Cargo builds the one reqwest with it for Siphon's client too), but hyper-util takes `ProxyServer` word for word as one address, so only a plain `host:port` worked: with the per-kind form `http=…;https=…` (what Windows writes when "Use the same proxy server for all protocols" is off) the checks went straight to GitHub, around the proxy, and with `socks=…` every check failed, so a first launch couldn't have installed the tools. Measured 2026-11-19 with the dev build and a logging proxy, before and after: with no proxy, the checks reached GitHub directly; with `127.0.0.1:18080`, `http=…;https=…`, `socks=…` (as SOCKS4) in Windows' settings and with `ALL_PROXY=socks5h://…`, the three tool checks, `latest.json` and its redirect all went through the proxy, and Siphon made no other connection. Before the change, `http=…;https=…` had connected to GitHub directly, and `socks=…` failed with "error sending request". The installer download that follows an app update uses the same client settings, but wasn't run, as there was no newer release to install.
- **The proxy connects to a site the way browsers do** (2026-11-21, "Happy Eyeballs", RFC 8305, `proxy::connect`): a name's IPv6 and IPv4 addresses take turns, the next is tried beside the last every 250 ms or as soon as one fails, and the first to answer is kept. Until 0.15 it tried them one after another, IPv6 first, and an address that never answers held the connection for Windows' 21 seconds before the next. Found on the test PC, whose IPv6 didn't reach Twitch's video servers (CloudFront: `curl -6` timed out, `curl -4` connected in 15 ms) while it reached Twitch's playlist servers: every segment of a recording waited out the 30-second limit and the recording stalled after its first six seconds, though ffmpeg and curl on their own (which do the same as browsers) recorded fine. After the change, a recording on the same network ran at the stream's rate from its first second.
- **A site the proxy can't reach** is answered with `502 Siphon couldn't reach the site (…)`. yt-dlp then reports "Tunnel connection failed", which `errors::classify` treats like any other lost connection, so the download is tried again. Connecting, a SOCKS handshake and an HTTP proxy's answer to `CONNECT` each give up after 30 seconds; until 0.13.1 an HTTP proxy that took the connection and never answered held it forever.
- **The one-click limits are 20, 30, 40 and 50 MB/s** (changed 2026-11-17, before 0.8.0 was published, from 2, 5, 10 and 25). The limit is stored as a number of bytes per second, not as a choice from the list, so a limit saved with an old preset is kept exactly as it was and shows as **Custom** with its value. Nothing has to be migrated, and changing the list again never changes anyone's limit (`limits_from_old_presets_are_kept_as_they_were` in `settings.rs`).
- **MB/s means MiB/s**, the unit Siphon shows speeds in, so "Limited to 5 MB/s" and a speed of "5.0 MB/s" agree. The setting is stored in bytes per second (`speed_limit`, `null` for unlimited), between 0.1 and 1000 MB/s.
- **Measured live** (2026-11-17, three downloads at once: a 4K YouTube video, an archive.org video and a 40-second trimmed part of the 4K video). At 5 MiB/s the folder grew at 5.02 MiB/s (1.74, 1.84 and 1.44 each), and the app's own measurement stayed between 4.97 and 5.19. Changed to 2 MiB/s mid-download, the proxy's rate dropped to 2.03 within a second. On disk it settled at 2.00 MiB/s within about 4 s, because yt-dlp writes in large blocks. After a restart the limit was still on, and a new download ran at 4.99 MiB/s.
- **Each download's speed and time left are measured by Siphon**, over the last three seconds of its byte counts (`Tracker::measure`), the same way as for trimmed parts. yt-dlp's own speed is a reading over a moment, and YouTube arrives in 10 MB requests, so it jumped at every request: under a 20 MiB/s limit it read up to 65.8 MiB/s, and a third of its readings were over 21, while the file grew at 18.8 MiB/s. Measured from the byte counts, the highest reading was 21.5 and 1% were over 21 (2026-11-17). The progress template no longer asks yt-dlp for its speed or time left. A new stream (the audio after the video) or a try that starts over is measured afresh, and nothing is shown for its first half second.

### Trimming

- **Every cut is on the exact frames, and Fast cut is gone** (2026-11-17, the owner's call). Fast cut copied the stream from the key frame before the start, up to a few seconds early; once exact cuts became fast too it had no reason to exist. The trim panel has no cut-mode choice, `Trim` has no `exact` flag, and an `exact_cut` saved in `choices.json` by 0.8 is read past and dropped.
- **Cuts do not use `--force-keyframes-at-cuts`.** Tested: with that flag yt-dlp re-encodes both video and audio with ffmpeg's defaults (the log showed VP9 at CRF 32 and Opus at 96 kbit/s), on the CPU, with no progress. yt-dlp downloads only the section (`--download-sections`, a second past the end so the last frames can be decoded), stream-copied, with `-copyts -start_at_zero` so it keeps the video's own timestamps. It starts at the key frame before the cut. Siphon then cuts it one of two ways:
- **Smart cut, for a copied H.264 or HEVC stream** (`src-tauri/src/ffmpeg/smart_cut.rs`, run by `DownloadManager::smart_cut`). Only the frames from the start to the first usable key frame, and from the last key frame to the end, are re-encoded; the rest is copied. Measured on Twitch 1080p60: 5 minutes cut in 3.5 s instead of 58 s, an hour in 20 s instead of 11.5 min (85 s with the download, against about 13 min); a YouTube 1080p60 part of 90 s took 6.8 s in all. The copied frames are bit-identical to the original, so the clip is smaller and better than a full re-encode. The steps:
  1. ffprobe lists the part's video packets (presentation and decode times, key flags), and a read-only `trace_headers` pass over the key frames says which are IDR frames (HEVC: IDR or CRA).
  2. Copying starts at the first **IDR** key frame inside the selection and stops before the last key frame. Both must be closed (no frame on one side shown on the other). The start has to be an IDR: YouTube mixes IDR and non-IDR key frames, and a decoder that meets a non-IDR frame after the re-encoded start keeps its parameter sets and reordering, garbling and then misordering the copied frames (found 2026-11-17).
  3. The start and end are re-encoded on the GPU (`cq 17`, visually lossless: about 50 dB) with the source's profile, level, pixel format and colour tags, every frame keeping its own timestamp in the source's time base (`-enc_time_base demux`). They have no B-frames, so their decode times are moved back by the source's reordering delay (`setts`) to keep decode order rising across the joins.
  4. The middle is copied by picking packets on their own timestamps (`noise=drop=…`), not by seeking: seeking lands a key frame early or late when a file doesn't start at zero, which cost three wrong attempts in testing. The source's parameter sets are put in front of every copied key frame (`dump_extra`), because MKV keeps them only in its header.
  5. The audio is copied by the same rule (packets whose middle falls inside the clip), or trimmed with `atrim` when it is converted. The pieces are joined as MPEG-TS on their original timestamps (`concat:`) and shifted to start at zero. The MP4 index is written into space reserved at the front (`-moov_size`, about twice the 17 bytes per packet measured, the audio counted at a hundred packets a second, and 64 KiB), not moved there afterwards with `+faststart`, which rewrote the file and cost half a minute an hour; if the space runs short, ffmpeg says so ("reserved_moov_size is too small") and the join is redone with `+faststart`. What the index doesn't use stays in the file as padding: until 0.17 the reserve had a megabyte more, so a 30 s clip carried 1.15 MB of nothing, enough to push a Share clip over its limit and have it converted after all. Measured 2026-11-22 with 64 KiB: a 60 s 1080p60 clip left 267 KB, and a 10-minute one used 1.1 MB of its 3.1 MB in one pass. HEVC in MP4 is tagged `hev1`, since its parameter sets change in the stream.
- **Every smart cut is checked, and anything uncertain is re-encoded in full** (`Recipe::with_full_cut`, the old path). The checks: every frame of the selection present at its own time, decode times rising, every copied audio packet at its source time (start, middle and end: no drift), the audio spanning the video, the start decoded side by side with the source (re-encoded frames at least 38 dB, the first 30 copied frames identical), and the end decoding cleanly. The fallbacks: the part not on the video's own clock, no frames, too short to copy anything, open GOPs, no IDR key frame inside, decode times that can't be lined up, a profile or pixel format the encoder can't match (H.264 High 10 or 4:4:4, HEVC Rext), a failed step, a failed check. Each is a unit test. `siphon.log` (`%LOCALAPPDATA%\app.siphon.desktop\logs`, `src/log.rs`) records each cut's path, the reason for a fallback and the time of every step.
- **Every converted file is checked for its picture** (or, for sound alone, its sound) before it is called finished (2026-11-23, `check_converted`, `Probed::has_content`). ffmpeg ends without an error when a cut finds none of its selection in the part, and writes a file with no tracks: a part of a Twitch VOD still being recorded, on the wrong clock (see below), came out as a 262-byte MP4, and the download said it had finished. Such a file is now deleted and the download fails ("the converted file came out empty"), its source kept for Try again like any failed conversion. It is not tried again by itself: the same part would come out the same.
- **Players:** smart-cut clips (Twitch and YouTube H.264, and an HEVC test clip) were decoded by Media Foundation, which Media Player uses, frame for frame like ffmpeg (its few low frames are scene cuts and its own re-encoding, as an untouched control showed); played in WebView2 across the joins with no dropped or corrupted frame and the right picture at each join; and played in VLC with no other messages than an untouched file gives.
- **Clips for iPhone / iPad / Mac are re-encoded in full.** Apple's players are strict about parameter sets that change partway through an `avc1`/`hvc1` stream, as they do at a smart cut's joins, and no Apple device was at hand to test.
- **VP9 and AV1 are converted when cut**, as before. A smart cut would need same-codec encoders (VP9 only on the CPU, AV1 on the GPU only on newer cards) and joins inside WebM/MP4 whose handling by players couldn't be made reliable; they mostly come from YouTube's 4K, which Watch converts anyway.
- **The cut in a conversion** uses a `trim` filter on the absolute timestamps and `-output_ts_offset -<start>`, and cuts the audio the same way as the smart cut. Audio on another clock than the video is moved onto it first (`smart_cut::clock_shift`, a second input with `-itsoffset`): archive.org's AVI derivatives come out of a section download with the video on the source's clock and the audio restarting at zero, which put the sound 56 s out of place (found 2026-11-17; it was wrong before the smart cut too). The audio counts as on another clock only when it starts neither with the video nor at the cut: on the same clock the video starts at the key frame before the cut, often seconds earlier, and the audio at the cut. Until 0.14.0 any gap over 2 s counted, so such a part's sound was moved early by the gap, out of step and short at the end (found 2026-11-20: a YouTube part cut at 4 s from a key frame at 0 came out with 5 s of sound in 8; now its sound starts at the source's 4.000 s, by cross-correlation, and archive.org's AVI is still moved by 56.125 s).
- **Section timestamps count from the start of the video** (`-start_at_zero` next to `-copyts`). YouTube's streams start at zero, but Twitch's start about a minute in, so "1:00:00" was timestamp 3659 in the downloaded section. The cut window then held no video frame at all, and an exact cut came out as audio only (found 2026-11-17 on a Twitch VOD).
- **A section is written as MP4 even when yt-dlp takes the video for live** (2026-11-23, `--no-hls-use-mpegts` in `args::recipe_args`). yt-dlp calls a Twitch VOD that is still being recorded live (`live_status: is_live`). For a video it takes for live, it writes a section as MPEG-TS and then copies it into MP4 without `-copyts`, which moves the part to zero: 600–631 s of a VOD came out at 0–39.5 s, the smart cut found none of the selection in it, and the full cut it fell back to made an empty file (see the check above). Written as MP4 at once, as yt-dlp does for any other video, the part kept its place (591.5–631.0 s). For a video yt-dlp doesn't take for live this is already the default: a finished VOD's part came out byte-identical with and without it. Measured in the dev build: 10:00–10:30 of a VOD being recorded was smart-cut in 5.7 s, 1800 frames, each the VOD's own frame at its time.
- **The preview plays HLS streams directly** when the site has no plain file. WebView2 (and Safari) play HLS in a `<video>` element natively, seeking included, and a media element needs no CORS headers (Twitch's CDN sends none, which rules out hls.js). Plain files still come first. Before this, an HLS-only site fell through to the preview copy, which for a seven-hour Twitch VOD meant downloading 2 GB before showing anything.
- **A stream with a bitrate but no size gets one estimated** (bitrate × duration, `estimate_size` in `src-tauri/src/ytdlp/metadata.rs`). yt-dlp usually does this itself, but not for Twitch. Without a size, a trimmed part had nothing to measure its `.part` file against and sat on "Preparing" until it finished.
- **Each trimmed part is its own download** and its own file, named `Title [id] (1m00s-1m15s).ext`. The backend takes one trim range per job; the UI starts one job per part.
- **A cut never changes the resolution a preset picks.** It keeps a copied H.264 or HEVC stream a copy (smart cut), and converts anything else to the device's conversion target.

- **Section downloads report no progress** (they go through ffmpeg inside yt-dlp), so progress is read from the growing `.part` file against the expected size, every 250 ms. Speed is the file's growth over the last three seconds (ffmpeg writes in bursts, so one step swings wildly), and the time left is the bytes still expected at that speed. Once the file passes the estimated size, the time left is shown as unknown rather than zero.
- **A trimmed part gives up on a stalled connection after 20 seconds** (`-rw_timeout`, `SECTION_READ_TIMEOUT` in `ytdlp/args.rs`). Without it ffmpeg waited forever. But on a timeout ffmpeg ends as if the part were complete and yt-dlp reports success, with a truncated file. So Siphon also asks ffmpeg for its errors (`-loglevel error`; yt-dlp silences them otherwise) and treats "Error during demuxing" or "partial file" in the log as a dropped connection (`errors::section_cut_short`): the file is removed and the download tried again. The part's length was tried first and rejected: a part can legitimately come out shorter than the selection when key frames are far apart. Tested with a local server that stops sending partway: the first try stalled, was caught after 20 s, and the retry completed; YouTube and Twitch parts raised no false alarm.

### Queue and settings

- **Pausing kills the process and keeps the partial files.** yt-dlp has no pause command.
- **A paused or failed download keeps a record of its files** (`leftovers` in `src-tauri/src/downloads/mod.rs`, by download id). The next start under the same id, whether **Resume**, **Try again** or an automatic retry, runs without `--no-continue`, so yt-dlp continues from its `.part` file, and a source that was already downloaded goes straight back to converting. A new download runs with `--no-continue`, which makes yt-dlp ignore partial files of the same name. The backend decides which applies; the frontend doesn't say. Section (trimmed) downloads are written by ffmpeg, which can't continue a file, so they start over.
- **A download never touches a file that was already there; a second copy gets its own name** (`Title [id] (2).mp4`, then `(3)`, …). Until it is finished, everything a download writes to the folder carries its own marker (`Title [id].siphon-1a2b3c4d.mp4`, `args::own_marker`, from the download id), so it stays the same for every try at that download and later tries carry on from its files. When yt-dlp is done, Siphon renames the file to its final name (`publish`), taking the next free number when a file or another running download (`DownloadManager::claimed`) has the name; converted files are named the same way (`unique_output`). Replaced (2026-11-18) an approach that read the name yt-dlp announced and stopped it when the name was taken: by then yt-dlp had already counted an existing file as "already downloaded" and run its fix-ups on it, so an M4A of a video was rewritten when its MP3 was downloaded, and a `.temp.m4a` could be left behind. A marked file can never be one the user had.
- **Each stream file says whether it is an intermediate** awaiting a merge, rather than one flag per download. Cleanup deletes intermediates but only the `.part` companions of anything else, so a retry that picks different streams can never delete a finished file. A trimmed part is never an intermediate: it arrives under its final name.
- **The queue is first in, first out behind one gate.** A job runs when it is first in line and fewer than the configured number are running. The limit is read each time, so changing it in Settings takes effect at once.
- **Settings live in the backend** (`settings.json`), not in browser storage, because the backend is what uses them.
- **The last choice and saved presets live in `choices.json`**, also in the backend, separately from `settings.json` so the Settings panel can't overwrite them. Up to 0.6 the choice was in the webview's storage (`siphon.options`); the frontend hands it to `import_legacy_choices` once, and `choices::from_legacy` maps the old preset ids (the only place they still appear). Custom stream picks are not remembered: they belong to one video.
- **A conversion's source waits in a work folder** (`<app cache>/work/<download id>/`) until the finished file is written and checked; the output is written as `Title.converting.ext` and renamed at the end. A failed or paused conversion keeps its source, so **Try again** or **Resume** goes straight back to converting. Work folders are removed on success, on cancel, when the app closes, and at launch if older than a day.
- **Custom file names can't contain folders or `..`** and must contain at least one yt-dlp field. The folder is its own setting, and a name without fields would make every download overwrite the last.
- **Errors say whether they may pass** (`Retry` on `AppError`, which the frontend never sees). A dropped or refused connection, HTTP 403 and 5xx errors get two more tries, after 2 and 10 seconds; HTTP 429 gets one, after 30 (`run` and `Retries` in `src-tauri/src/downloads/mod.rs`). Each schedule counts its own tries: until 0.13.1 they shared one count, so a 403 followed by a 429 gave up without the 30-second wait (tested 2026-11-20 with a local server answering 403, then 429: the download waited 2 s, then 30 s, and finished). A bot check is not retried, because asking again straight away makes a site more suspicious. Its message says the check usually passes on its own within hours and that Nightly sometimes gets through sooner; it used to say an update usually fixes it, which wasn't true when YouTube had flagged the connection itself and the newest yt-dlp got the same check (2026-11-17). An "outdated" error still updates yt-dlp first and tries again with it; if yt-dlp is already current, or the update has to wait for other downloads, it falls back to the pauses above. The wait shows as its own stage ("Trying again in a moment") and ends at once if the download is stopped.
- **The cost of those retries:** being offline takes about 15 s to report instead of 5, and a connection lost in the middle of a download takes about 80 s to give up.
- **The download list is kept between sessions** (2026-11-18). The frontend keeps the list in the webview's storage (`siphon.downloads`, the newest 200 finished ones), and the backend keeps what paused and failed downloads left on disk, and which files were finished, in `downloads.json` next to `settings.json` (`SavedState` in `downloads/mod.rs`). Downloads that were running or waiting when Siphon closed come back paused; **Resume** (or **Resume all**) carries on from their files under the same id. Once the list is restored, `forget_other_downloads` removes the files of downloads it no longer has. Launch-time cleanup of work folders skips those of kept downloads.
- **"You already have this" comes from the download list** (2026-11-18, `src/features/video/AlreadyDownloaded.tsx`). A finished download whose link matches the open video's counts, and the link is the site's canonical page (`webpage_url`), so `youtu.be/…`, `&t=30s` and `watch?v=…` all match. Nothing new is stored but the time it finished (`finishedAt`; downloads from before 0.11 show no date). It only knows the list: after **Clear finished**, or once a download is one of more than 200 finished, it's forgotten. A file that was moved or deleted doesn't count, checked with `files_present`, which answers only for files Siphon downloaded (like `open_file`). Downloads started from the same screen are left out, because the Download button already shows them.
- **Finish notifications are shown from Rust** (2026-11-18, `commands::notify` with `tauri-plugin-notification`), so the webview has no notification permission and no extra npm package, as with the app update. The command does nothing while Siphon's window is focused. The frontend (`src/lib/notices.ts`) gathers what finished or failed within two seconds into one notification, so a playlist doesn't stack twenty. In the dev build Windows shows them as coming from PowerShell, since Tauri borrows its app identity there; the installed app shows its own name. Tested 2026-11-18: with Siphon minimised, a finished clip's notification reached Windows' notification history ("Download finished · Me at the zoo (0:02–0:06) · 219 KB"). The pop-up itself depends on Windows' Do not disturb setting.
- **Closing the app pauses every download** (`DownloadManager::shut_down`, 2026-11-18; it used to cancel them and delete their files). Each one's yt-dlp or ffmpeg process ends, its files are recorded, and the next session carries on from them. A job that hasn't ended within three seconds still loses its proxy listener.
- **Closing while downloads run or wait asks first** (`src/components/CloseGuard.tsx`, 2026-11-18). It catches every way of closing (title-bar button, Alt+F4, the taskbar) through the window's close-requested event, which is why the capability includes `core:window:allow-destroy`: the event's handler destroys the window itself once it lets the close through. Keep downloading is the default button.
- **One Siphon at a time** (`tauri-plugin-single-instance`, 2026-11-18). Opening it again brings the open window forward, un-minimised, instead of starting a second copy that would share its settings, download state and preview cache. The dev build has its own identifier (see Distribution), so it runs beside the installed app.

### Sign-in

Added 2026-11-18. How it works, and how to test it, is in [sign-in.md](sign-in.md).

- **Siphon hands over cookies; yt-dlp does the signing in.** Every site logs in differently, and yt-dlp already knows how to use each one's cookies. Siphon only gets the user's cookies for a site, keeps them, and gives each download its own site's. Nothing is special-cased per site except a short list of sign-in pages and session cookie names, which only make the window more convenient.
- **Without an account first, always; an account only after the site refused** (2026-11-18, the owner's rule: never ask for an account a video doesn't need). Every lookup and download goes without one, even on a site Siphon is signed in to (`Sessions::lookup`), unless the site is set to **Always** or the user asked. This also keeps less of the account's activity on record, and kept public Instagram posts working while yt-dlp's signed-in Instagram requests failed. Measured on the owner's PC with YouTube signed in: *Me at the zoo* and *Big Buck Bunny* were found without the account (about 3 s); an age-restricted video was found with it, by itself, without a prompt (about 7 s, the refused try included).
- **Each refusal says how likely an account is to help** (`Chance`: needed, maybe, risky, unknown, never), and the card follows it: the prompt opens for a login wall or a "maybe" (members-only, Premium-only, a private video shared with you, a Patreon tier), the bot check and unrecognised errors only get a quiet link, and DRM, removed, region-blocked, bought or password-protected videos and lost connections get nothing. **No thanks** folds an open prompt into the quiet link. Before, sign-in was offered only for a login wall, and members-only, Premium-only and shared private videos were wrongly treated as hopeless; and a members-only video refused with the sign-in would have been called a run-out sign-in.
- **Once signed in, a site isn't asked again.** A Needed or Maybe refusal is retried with the sign-in by itself; Risky and Unknown get "Try with your sign-in" instead. A Maybe refused with the sign-in says the account has no access; only a login wall that refuses it means the sign-in ran out.
- **The download goes the way its lookup went** (`VideoInfo::with_account`): some sites tie stream links to the session that asked for them. A download refused without an account is retried once with the sign-in, looking the video up again with it.
- **Each way is checked before it's kept.** The lookup that failed runs again with the new cookies; only if it gets past the sign-in are the site's cookies saved, so a sign-in that doesn't work never replaces one that does. "Past the sign-in" includes failing with an error of the video's own (removed, unreadable): found 2026-11-18 on Instagram, where the owner had signed in but the test post then failed with HTTP 400, and Done could never finish. A failed connection, a bot check or a refusal don't count (`sign_in::past_the_wall`).
- **Three ways, in this order** (the owner's spec): Siphon's sign-in window (works whatever browser the user has, or none), a browser on this computer, a cookies.txt file. The suggested one is the window, then Firefox, then whatever hasn't failed for that site this session.
- **One jar per site, encrypted with DPAPI** for the Windows user, in `%LOCALAPPDATA%` (not the roaming folder: cookies shouldn't follow a profile to another computer). The index beside it holds no cookie.
- **A download gets only its own site's cookies**, in a temporary file that belongs to the job's record like its proxy listener, and goes the same ways (see Speed limit). YouTube's site is `youtube.com` alone, not `google.com` too: yt-dlp needs only the former, and the latter is the whole Google account.
- **Renewed cookies are written back as differences**, not as the whole file, so downloads running at once don't undo each other's renewals.
- **The sign-in window is one window with two webviews** (Tauri's `unstable` feature): Siphon's bar with Done, and the site's page under it, in a WebView2 profile of its own per site. A separate window for Done, or a bar drawn into the site's page, were the alternatives; the first splits one task over two windows, the second puts Siphon's buttons inside someone else's page. A profile per site keeps sites apart and makes Sign out a folder delete.
- **Google's refusal of embedded sign-in is answered, not worked around.** When Google won't sign in inside the window ("This browser or app may not be secure"), Siphon says so and suggests Firefox or a cookies.txt file. It doesn't change its user agent or anything else to get past the check. On 2026-11-18 Google let the owner sign in to YouTube in the window.
- **Chromium browsers on Windows mostly can't be imported from**, and Siphon says why instead of failing vaguely. Since 2024 Chrome, Edge and Brave encrypt cookies so only the browser can read them. Measured 2026-11-18: Edge and Brave both refused in about 1.3 s ("Failed to decrypt with DPAPI"), Brave also while running.
- **The cookies.txt dialog opens from Rust**, like the other file access, so the webview can't name a file for Siphon to read.

### Live recording

Added 2026-11-19. How it works, what was measured and what is known not to work: [live.md](live.md).

- **Recorded as MPEG-TS, made into the preset's file afterwards.** A crash, a power cut or a killed process leaves everything up to that moment playable; the finished file is only made, checked, and the recording removed, once it has ended. If it can't be made or fails its checks, the recording is kept as recorded rather than lost.
- **Stop is Ctrl+Break, not a kill.** yt-dlp runs in its own process group; `siphon.exe --siphon-interrupt <pid>` (a helper, since only a process on the same console can send it) breaks it, and Siphon waits for the ffmpeg under it to finish its file. Plain Ctrl+C was ignored in testing.
- **No Pause for recordings:** a live stream doesn't wait. Closing Siphon stops them gently; they are finished at the next start ("Recovered"), from the files `downloads.json` lists as they appear.
- **Everything Siphon starts ends with it** (a job object, `process::end_with_siphon`), for downloads too: before, a crash left yt-dlp and ffmpeg running, which for a recording meant a file growing with nobody to stop it.
- **Siphon waits for a stream itself** rather than with `--wait-for-video`, so the quality is planned from what the stream offers once it starts.
- **Recordings skip the queue and go first within the speed limit**, up to their stream's bitrate and a quarter more: one that falls behind misses parts of the stream.
- **Share is not offered for a stream as it airs**, nor Trim: they make a file from the whole video.
- **A converted recording keeps its stream's frame rate** (2026-11-21, `-r` in `ffmpeg::finalize_args`). An MP4 is made at one frame rate, which ffmpeg takes from the start of what it reads, and a Twitch recording starts with the ad Twitch shows viewers without an account, at 30 frames a second: until 0.15, the 60-frame stream after it lost every other frame whenever the recording was converted (its chat drawn in, say). It is now made at the rate of the stream's format; the ad's frames are shown twice, which costs next to nothing.
- **Twitch's ads are left out, without an account** (2026-11-22, `downloads/twitch_feed.rs`; the owner asked for it, rather than a sign-in with a subscription). A Twitch recording from now reads a playlist Siphon serves on 127.0.0.1, made from Twitch's; yt-dlp records it as any stream (`--load-info-json`, the served playlist as the chosen format's stream), so Stop, dropouts, crashes and recovery are unchanged. Each part reads the stream's **VOD** where the channel keeps one: Twitch saves it without the ads, so nothing is missed while an ad plays, and the chat is on the VOD's clock. Otherwise the **stream without the ads** (the segments not titled `live` left out); the recording then jumps over each ad, as Twitch doesn't send what airs during it. If neither can be had, the stream is recorded as before, ads and all. How it runs: [live.md](live.md#twitchs-ads).
  - **A recording without the ads starts with the newest segment, alone in the first playlist served**, so where it starts and when that aired are known exactly, with no frame match; each jump is where the lengths of the segments served before it put it, because ffmpeg closes a jump of over 10 s up (its `dts_delta_threshold` for formats with timestamp discontinuities, as HLS is). Tested by taking 12 s of a live stream's segments out of a served playlist: continuous picture and sound, together, and the next segment exactly where its offset said.
  - **Read from the VOD, Stop records on to the moment it was pressed** (the VOD's second that aired then, from when the VOD was created), and the served playlist ends there; the progress says how much is left, a second Stop stops at once, and after three minutes it stops anyway. Without this, the end of a recording would lag the stream by the VOD's delay. It took 8 to 15 s in testing.
  - **A VOD that stops growing for a minute is answered "not found"**, as Twitch answers a dropped stream's playlist (otherwise ffmpeg would wait on it for hours: it reloads a playlist without new segments up to 1000 times). The recording then waits for the stream as for any, and reads its later parts without the ads, in case the VOD itself is what stopped.
  - **yt-dlp adds the date and time to a live stream's title each time it reads a lookup**, so the served lookup's title is the one from before that (`fulltitle`): otherwise files were named `dona (live) 2026-11-22 03_10 2026-11-22 03_11`. Read from the start, as the VOD is, it adds nothing, so the VOD's lookup gets the stream's title as it is, and the recording is named as one from now always was.
  - **The VOD's lookup comes from yt-dlp** (`--live-from-start`), which names the VOD the stream is saved to; Twitch's GraphQL `archiveVideo` was used for that before and is no longer needed. A channel without VODs makes yt-dlp say "no formats that can be downloaded from the start", which is read as "no VOD" (`errors::not_kept_from_start`).
- **A stream as it airs is never downloaded for a preview** (2026-11-21, `preview::source`). Its preview would be Twitch's ad for viewers without an account, and when it didn't play, the last resort downloaded a "small copy" of a stream that doesn't end: yt-dlp recorded it in the background for up to 15 minutes. Where a live stream needs a picture (placing its chat), it gets a still of the stream instead: Twitch's live thumbnail, the whole frame, at most five minutes old.

### Subtitles

Added 2026-11-20. How it works, what was tested and its limits: [subtitles.md](subtitles.md).

- **A language is remembered, not a track** (`subtitles` in `choices.json`), and travels inside the `Choice`, so planning, size estimates, playlist downloads, retries and resumes all carry it without plumbing of their own. A new user starts on Off (the owner's call). Another language is never put in place of a missing one.
- **People's subtitles before speech recognition, and no machine translations.** YouTube refused every translation asked for in testing (four of four, HTTP 429), so offering them would offer what almost never comes. They are told apart from speech recognition (YouTube's `-orig` key) and left out in `ytdlp::subtitles::read`.
- **Fetched by a yt-dlp of their own, beside the video** (`--skip-download`): a subtitle failure must never fail a video, and fetched in the same run as the video, it does: a 360p download asking for a translation YouTube refused stopped with exit code 1 and wrote nothing (tested 2026-11-20). Until 0.14.0 this run came after the video and looked the video up again, about 3 s on YouTube; now it starts with the video, from the same saved lookup (see Download speed), so it costs the download no time of its own. If the video fails, the subtitles' run is ended with it. A job's processes are a list (`Job::pids`), so Pause and Cancel end both (tested 2026-11-21: paused and resumed, then cancelled at 30%, with English subtitles; nothing left running and no files).
- **SubRip is asked for first.** YouTube's WebVTT for speech recognition repeats each line as it rolls up, with a timing tag on every word, and converted it comes out as junk; its SubRip is clean but overlaps, which `srt::prepare` splits into cues that don't (an MP4 track can't hold overlapping cues).
- **Where a track goes is decided by where it shows, not only by what holds it.** Windows' own playback found subtitle tracks in MKV but not in MP4 or WebM (tested with `Windows.Media.Playback`), so Windows gets MKV; TVs and Max quality too; Apple and Android keep MP4 timed text, tagged `tx3g` (ffmpeg tags MOV's `text` unless told, which QuickTime ignores).
- **A smart cut is joined and checked as MP4, then copied into MKV.** Its checks read decode times, which Matroska doesn't keep; every smart cut into MKV failed them and was re-encoded in full (Custom MKV clips had the same problem before subtitles).
- **Share draws them into the picture** (libass, in the encode), since chat apps show no tracks; an original that would fit is encoded anyway, to the same budget.
- **Drawn-in subtitles are read by file name from ffmpeg's working folder**, the download's work folder: a Windows path inside a filter's arguments needs escaping twice over.

### Chat

Added 2026-11-21. How it works, what was measured and its limits: [chat.md](chat.md).

- **What it is** (the owner's calls): Twitch's chat drawn into the picture, as a *With* or *Without* choice, always in one file, for VODs and for streams recorded live, from now or from the start. Every emote: Twitch's own, 7TV, BTTV and FFZ, animated; 7TV's personal emotes and name paints left out. The box goes over the picture where the user places it on the preview, remembered per channel; mostly transparent and slightly darkened. The text is plain, with no outline or shadow (2026-11-22, the owner's call): until 0.16 each glyph had a dark "outline" made by swash's `embolden`, which grows a glyph only rightwards and upwards, so it was in fact a shadow 5–6 px above and right of every letter at 1080p and nothing below or left, and read as black smears behind the text. The wait is kept as short as it can be. Twitch's ads are left out of a recording (2026-11-22, see Live recording).
- **Offered with Max quality and Watch**, the presets that keep the picture as it is: drawing chat in means encoding it anyway.
- **Read without an account.** A replay from Twitch's GraphQL API with the web player's public client ID, as yt-dlp does, paged by offset (paging by cursor fails Twitch's integrity check without a browser token); a stream's chat from anonymous IRC. Twitch keeps at most 15 messages a second in a replay, so a VOD's chat is thinned in its busiest moments, while a recording keeps everything.
- **The fastest encoder setting, capped at one and a half times the source's bitrate.** The same quality setting at NVENC's p1 instead of p5 scored VMAF 97.18 against 97.27, with files about 27% larger, made 2.75 times faster. Twitch's busiest scenes uncapped took 2.3 times the source's bitrate.
- **A recording is timed by what it reads**: read from the VOD, by the VOD's clock; read without the ads, by the program dates of the segments served (the first, and the first after each ad left out). Only a recording of the stream as yt-dlp reads it, ads and all, is timed by finding a frame, not by the ingest times Twitch's segments carry: keeping the data track they are in made ffmpeg abort at the switch from an ad to the stream. A recent segment's first frame is found among the recording's last frames; its playlist says when it aired.
- **Chat is shown where Twitch's replay shows it**, 5 s before the moment it was sent aired (2026-11-21, `REPLAY_LEAD`). Placed by when it aired, a recording's chat came 4–6 s later than on Twitch's replay of the same stream, and than in Siphon's own downloads of its VOD: the replay counts from when the VOD was created, 4.3–5.8 s after the stream's first frame aired on three channels. That is also about how far behind live viewers watch, so reactions come just after what they react to. Checked frame by frame against a recorded stream's VOD: each message within 0.81 s of the replay.
- **Read from the VOD, the replay gives what was said before IRC was read** and IRC the rest, joined at IRC's first message. yt-dlp records a Twitch stream from the start from its VOD, and Siphon reads one from now from it too, so the recording is on the VOD's clock and needs no frame match. Until the replay is fetched (two minutes in), the VOD's clock is taken from when the VOD was created, to the second: 1.70 and 0.30 s out on two channels (2026-11-22).
- **Drawn in as it records**, in two-minute pieces once their chat has settled (2026-11-21, `downloads/live_draw.rs`). Drawing runs at about 14 times real time, so finishing a three-hour stream after Stop took about 13 minutes; now only the last few minutes are drawn after Stop, and the drawn pieces copied into the file (a 7-minute recording was finished 19 s after Stop). The pieces wait two minutes and a quarter so that deletions and timeouts, which the finished file leaves out, have come. Anything that goes wrong falls back to drawing it all after Stop, as before. The joins are exact (`draw_piece_args`): the recording is read from 10 s before a piece, since MPEG-TS has no key frame index and a seek from 3 s before could land past a key frame; the frame rate is made in the filter graph before the cut, since `-r` after it added a frame or two past the cut; pieces are marked as starting afresh (`+initial_discontinuity`), since the first packet after a join was otherwise taken for a damaged one; and each piece is checked before it is added (`piece_fits`).
- **The chat layer never outlasts the picture** (2026-11-21, `ChatLayer::end`). ffmpeg's overlay goes on for as long as either of its inputs does, and the layer was fed a second longer than the picture "to be safe": a 30 s VOD clip with chat came out with 31 s of picture, its last second frozen and silent, and pieces drawn as a stream records overlapped by a second, which cost the sound 0.77 s at each join. The layer is now fed for the picture's length only (should it end a frame early, its last frame stays), and a clip or a piece is cut where it ends.
- **The preview lets go of what nothing shows** (2026-11-22, `chat::preview`): a live channel's 15 s after its view stops asking (it asks every second), and its chat stops being read; a video's five minutes after it was last drawn (asked again, it fetches its chat again). Before, a video's chat, layer and decoded emotes stayed until Siphon closed, and a live channel's chat was read until another live channel's preview was opened.
- **Every chat request is tried again** (2026-11-22, `chat::send`): twice, 2 and 6 s later, after a dropped connection, a server error or "too many requests", never after a refusal. A recording missing some of its channel's emotes or badges looks for them again every minute, ten times, keeping the most complete set. Before, a moment's failure of 7TV, BTTV, FFZ or an image's CDN cost a whole video those emotes, drawn as words, with only a log line to say so.
- **A recording is read from its own timestamps' start** (2026-11-22, `ffmpeg::seek_from`): ffmpeg counts `-ss` from a file's start, not by its timestamps, even with `-copyts` and `-seek_timestamp` (checked on a file starting at 101.4 s: `-ss 20` read from 121.4 s). Pieces drawn as it records and the frame match passed the file's own timestamps and worked only because recordings start at 1.4 s (checked on a Twitch recording from the start); they now subtract the file's start.
- **A recording stopped within two minutes still gets the chat from before Record** (2026-11-22, `live_chat::replay_for`, found by the owner in 0.16.1). Read from the VOD, a recording fetches the VOD's replay two minutes in, in a task that Stop ends. Finishing fetched a missing replay again, but only for the fallback that draws the whole recording at once; the chat drawn in piece by piece (`live_draw`) reads the replay from the work folder only, so it had none of it. The owner's 57-minute recording of a stream from the start, stopped about two minutes after Record, showed chat in its last 113 s only, though finishing had fetched 26,446 messages. Reproduced on two channels in the dev build; the same stream recorded side by side and stopped after three minutes had chat throughout. Finishing now keeps the replay it fetches, and first waits until two minutes after Record (`replay_wait`): fetched at once (95 s after Record), the replay lacked the last 25 s before it, at 5 to 12 messages a second, which it had later, and the box sat frozen for those seconds. The wait is left as it is rather than shortened by checking what the replay has, because a quiet chat looks the same as a replay that hasn't caught up. The row says *Fetching chat* meanwhile, and leaves out its ✕, which while a recording is being finished would throw it away. Checked from the window: stopped 60 s after Record, *Fetching chat* for 72 s, then chat throughout, changing every 6 s across Record.

### Managed binaries

- **FFmpeg uses the `-shared` build** (a 91 MB download rather than 200 MB) and is refreshed at most every 30 days.
- **Each tool lives in its own folder**, so an update is a folder rename and a rollback is the reverse.
- **A tool is never swapped while it is in use.** Everything that runs a tool holds a shared lock (`BinaryManager::in_use`); the swap needs it exclusively and gives up at once if it can't have it.
- **An update that can't swap right away is put off, not queued.** Making it wait would also block new downloads behind it. Whether it can swap is checked before the new version is downloaded as well as after: until 0.13.1 only after, so while downloads went on, a due FFmpeg update fetched 91 MB every hour and threw it away (tested 2026-11-20: with a recording running, Update now returned in 0.5 s and downloaded nothing; with nothing running, it installed FFmpeg in 5.5 s). The daily loop retries within the hour, because a round with a deferred swap doesn't count as "checked".
- **Ask-first mode still installs missing tools.** Only newer versions wait for a go-ahead; without the tools the app can't work at all.
- **Release-note summaries are derived, not copied.** For yt-dlp: the sites listed under "Extractor changes" ("Fixes for youtube, tiktok and 3 more sites."). For Deno: the first bullet. FFmpeg builds have no notes. See `src-tauri/src/binaries/notes.rs`.
- **Only updates get a toast.** First installs are shown by the setup screen.

### Interface

- **The accent colour is aqua/teal.**
- **The theme follows the system unless the user picks one** (Settings → Appearance). Each colour token in `src/index.css` holds both values with `light-dark()`, and `color-scheme` on `<html>` picks one: `light dark` follows the system, and `data-theme="light"` or `"dark"` pins it. One set of tokens instead of two copies, and scrollbars and text fields switch with it. The choice is kept in the webview's storage (`src/stores/theme.ts`), not in `settings.json`, because only the interface uses it, and it is applied before the window is first shown, so there is no flash of the other theme.
- **The focused link field has one crisp aqua edge and a soft glow** (2026-11-23, `LinkInput.tsx`, `--primary-glow`). It had a 60% aqua border inside a 4 px band of tint, which read as two muddy outlines. Now the border is near full strength, with a 1 px hairline of light and a 36 px glow around it, stronger in dark than in light, where a glow looks grubby. Rest and focus have the same shadow layers, so the light grows out of the edge over 300 ms instead of jumping on. A link that isn't one turns the edge, glow and icon red the same way.
- **Whatever can be clicked shows the hand** (2026-11-23, the owner's call, `index.css`): buttons, which every control in Siphon is (tabs and choices included), a list's options and sliders; not while disabled. The scaffold had kept the arrow over buttons, as native Windows apps do, which left nothing to say a control could be clicked.
- **Settings are grouped lists.** Each setting is one row in a card: its name, with a small control (a switch or stepper) on the same line, and a plain explanation underneath at full width. Wide controls (the folder, the file-name picker) go below the explanation. Squeezing the explanation into a column beside the control made it wrap into four or five ragged lines.
- **The download list is ordered as a queue:** running, then waiting in start order, then paused, failed and finished (newest first).
- **A download's row leaves things out whole rather than cutting them off** (2026-11-18). The panel leaves about 170 px for text beside the buttons, and a one-line "Done · 860 MB · 0:00.00 – 24:30.00" was cut mid-word. Now the title has two lines, and the status line is a row of short pieces, most important first (`statusPieces` in `QueueSheet.tsx`): progress, then the clip, the time left and the speed. A piece that doesn't fit wraps onto a hidden second line, so it disappears whole. The list uses short stage names ("Waiting", "Converting 67%", and only "42%" while downloading), a ✓ for done, and clip times without hundredths on whole seconds (`formatShortTimecode`). Hovering a row that left something out shows the full title and status (`Hint`'s `when`); a row that fits shows nothing.
- **The slide-over panels sit inside the error boundary**, so a panel that fails to render shows an error card instead of blanking the window. This came from a real crash: a Zustand selector that returned a new array on every call.
- **`scrollIntoView()` returns a promise**, so it must not be the return value of a `useEffect` (React would call it as a cleanup).
- **`open_file`, `reveal_file` and `files_present` only accept files Siphon downloaded** (this session or one it remembers in `downloads.json`, if the file still exists), so the webview can't use them to launch arbitrary paths.

### Distribution

- **The dev build keeps its own folders** (2026-11-19, `DEV_SUFFIX` in `main.rs`). Debug builds add `.dev` to the identifier at startup (`app.siphon.desktop.dev`), and every folder Tauri resolves follows it: settings, `downloads.json`, sign-ins, tools, caches, logs and the WebView2 profile. Before, both builds shared one set, so testing could sign the owner out, change their settings, or delete an installed copy's paused downloads: at launch each build told the shared backend to forget every download not in its own list (`forget_other_downloads`), and the two lists were separate. A first dev launch downloads the tools into its own folder. Measured: with the dev build started fresh, a download run, settings changed and the launch cleanup called with an empty list, the installed app's folders were byte-for-byte unchanged, and the installed app then ran beside the dev build without WebView2's `0x8007139F`.
- **App self-update uses GitHub Releases from the public repository.**
- **Updates are signed.** The owner approved (2026-11-16) generating a signing key. The private key is at `C:\Users\olimp\.tauri\siphon.key`, outside the repository, and in the GitHub Actions secret `TAURI_SIGNING_PRIVATE_KEY`. It has no password. The public key is in `src-tauri/tauri.conf.json`. If the private key is lost, installed copies can no longer be updated in place, so it needs a backup.
- **Releases are created as drafts.** The owner publishes them on GitHub, and installed copies see nothing until then.
- **The app update is driven from Rust commands** (`src-tauri/src/app_update.rs`), not the updater's JavaScript API, so the webview needs no extra permissions and no extra npm packages.
- **Siphon always asks before updating itself**, whatever the tools' "install automatically" setting says, because it has to restart. It refuses while downloads are running or waiting.

## Testing notes

- **Paths below are the installed app's.** The dev build's folders end in `.dev` instead (`%LOCALAPPDATA%\app.siphon.desktop.dev\…`, `%APPDATA%\app.siphon.desktop.dev\…`).
- **Presets:** over the DevTools protocol, call `plan_download`, `estimate_download` and `start_download` directly with a `choice`, then check the result with the managed ffprobe (`%LOCALAPPDATA%\app.siphon.desktop\bin\ffmpeg\ffprobe.exe`). To test the migration, delete `%APPDATA%\app.siphon.desktop\choices.json` and put an old state (`{"state":{"preset":"share","sizeLimitMb":50,"mode":"preset"},"version":0}`) in localStorage `siphon.options`. A 4K X video should copy for Apple at Best; none was at hand during the rework, so that case is covered by unit tests only.
- **Test links:** `https://www.youtube.com/watch?v=jNQXAC9IVRw` (19 seconds, a quick end-to-end check), `https://www.youtube.com/watch?v=aqz-KE-bpKQ` (10 minutes, 4K60: progress, presets, trimming, pause and resume), `https://www.youtube.com/playlist?list=PLa1F2ddGya_86Vmu2clTpAfBvBWnfLc9s` (20 videos: the playlist picker and the queue), `https://archive.org/details/BigBuckBunny_124` (a site other than YouTube), `https://www.twitch.tv/videos/2929613567` (a seven-hour Twitch VOD: HLS only, no stated sizes, timestamps that don't start at zero; Twitch deletes old VODs, so replace it when it goes).
- **To test a tool update without waiting for a real release:** close the app, change `tools.yt_dlp.version` in `%LOCALAPPDATA%\app.siphon.desktop\bin\manifest.json` to an older value, and start it again.
- **Retries and lost connections:** serve a file from a small local HTTP server that supports `Range`, can cut the connection after a set number of bytes, and then refuses requests for a set time. yt-dlp's generic extractor downloads `http://127.0.0.1:<port>/clip.mp4` like any other link, and the server's request log shows whether a retry continued (`Range: bytes=N-`) or started over. Point the download folder at a scratch folder first and set it back afterwards.
- **Closing the app:** use the window's Close button (over the DevTools protocol, the button with `aria-label="Close"`). `taskkill /IM siphon.exe` without `/F` did not end the app in testing, so it says nothing about the exit handler.
- **Speed limit:** measure from outside the app. Point the download folder at a scratch folder and sum the sizes of the files in it a few times a second. The app's own measurement arrives as `speed://total` events. `Get-NetTCPConnection -State Listen -OwningProcess <siphon pid>` lists the proxy listeners, one per running download, and none once they have ended. `set_settings` with a new `speed_limit` changes the limit mid-download.
- **Cuts:** start trimmed downloads over the DevTools protocol (`start_download` with a `trim`) and read `siphon.log` for the path each took and its step times. Check the result with the managed ffprobe: the frame count is the selection's length times the frame rate, and the audio's duration matches the video's. Good cases: a Twitch VOD (all IDR key frames), a YouTube 1080p60 part (Windows preset; mixed IDR and non-IDR key frames, in MKV), a Share part small enough to copy, an Apple part (re-encoded in full by design). To check a player, compare its decode with ffmpeg's frame by frame, and run the same comparison on an untouched source as a control: Media Foundation's own re-encoding and scene cuts produce dips that look like errors. Media Foundation can be driven headless through `Windows.Media.Transcoding` from PowerShell.
- **Subtitles:** start downloads over the DevTools protocol with `subtitles` in the choice (a language tag), then check the track with the managed ffprobe (`-show_entries stream=codec_name,codec_tag_string:stream_tags=language,title`) and its cues with `ffmpeg -i file -map 0:s:0 -f srt -`. Whether Windows' own players see a track: open the file with `Windows.Media.Playback.MediaPlayer` from PowerShell, play it muted and read the `MediaPlaybackItem`'s `TimedMetadataTracks`. A drawn-in subtitle shows in a frame taken with `ffmpeg -ss <time> -i file -frames:v 1 frame.png`. Good cases: *Me at the zoo* (English and German by people), the Rick Astley video (five languages by people, speech recognition in English, translations YouTube refuses), a TED talk (64 languages, WebVTT only, no names), a Blender overview (speech recognition only, rolling).
- **Sign-in:** see [sign-in.md](sign-in.md#testing): a local server that needs a session cookie covers every flow without a real account; the site's page in the sign-in window isn't reachable over DevTools, its bar is.
- **To listen for download events from DevTools:** `const T = window.__TAURI_INTERNALS__; await T.invoke("plugin:event|listen", { event: "download://event", target: { kind: "Any" }, handler: T.transformCallback((e) => console.log(e.payload)) });`
- **To drive the running app without touching the desktop:** start it with `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222` and use the Chrome DevTools Protocol at `http://127.0.0.1:9222/json` (screenshots, `Runtime.evaluate`, `Input.insertText`, mouse events, `Emulation.setEmulatedMedia` for light mode). `window.__TAURI_INTERNALS__.invoke(…)` calls backend commands directly.
- **While testing a recording, start the dev app with `npm run tauri dev -- --no-watch`.** Otherwise saving any file under `src-tauri` rebuilds and restarts the app, which cuts the recording short (it is then finished as Recovered at the restart). A background `npm run tauri dev` is ended at the tool's time limit, but Vite and `siphon.exe` go on running: stop them before starting it again, or it fails with "Port 1420 is already in use".
- **Chat:** find a busy live channel with Twitch's GraphQL API (`query{streams(first:15){edges{node{viewersCount broadcaster{login} archiveVideo{id}}}}}`, with the web player's client ID); a channel whose playlist has `#EXT-X-MAP` is served as CMAF. `siphon.log` says when the chat was read (`chat #<login>: reading it`), when the frame match placed the recording (`chat: stretch 1 aired … after it was guessed to`), and each piece drawn as it records (`chat: drew stretch 1 to …`). To check a recording's timing against Twitch's replay, take the stream's VOD (`archiveVideo`): the recording's chat clock against the replay's (`createdAt` and `tmi-sent-ts` are one clock), and its picture against the VOD's by matching frames (the VOD's timestamps start about a minute in). To check the joins of a drawn recording, list its packets' times with ffprobe (`-show_entries packet=pts_time`): every step should be one frame (1/60 s) and one audio packet (1024 samples).

## Known issues

- **Sign-in window: a host-only cookie becomes a domain cookie.** Tauri's cookie type drops the leading dot that tells them apart, so every cookie from the window is written for its domain and subdomains. It can't go past its own site, and no site tested minded.
- **Sign-in window: Done is needed on most sites.** It finishes by itself only where the session cookie's name is known (`site::SESSION_COOKIES`).
- **Taking over a sign-in from Chrome, Edge or Brave fails on Windows** (app-bound encryption, see Sign-in). Firefox, the sign-in window and cookies.txt files work. "Close the browser first" couldn't be reproduced on the test PC, where decryption failed first; its mapping is a unit test.
- **yt-dlp's signed-in Instagram lookups fail with HTTP 400** for posts that need the account (2026-11-18; others report it since October 2026). Public posts load with the session. Not Siphon's to fix; see [sign-in.md](sign-in.md#known-issues).
- **The README's screenshots are out of date** (2026-11-22): they still show the Edit tab, since removed, and the old group order (Audio now comes before Share). How they were made is in [development.md](development.md#screenshots); Twitch content can't be shown in them.
- **A Twitch VOD that is still being recorded opens as a live stream**, with **Record** and without Trim, because yt-dlp calls it live. Trimmed over IPC, it is cut correctly since 2026-11-23 (see Trimming); until then it came back "finished" as a 262-byte file. A channel's list of videos shows such a VOD as an ordinary video, and downloading it whole from there wasn't tried.

- **Intermittent HTTP 403 on section downloads.** A trimmed YouTube download once failed with `ffmpeg exited with code 3436169992`, which is ffmpeg's `AVERROR_HTTP_FORBIDDEN`. The same request succeeded on every retry and from a shell, so it is YouTube refusing a request now and then. Since 0.5.2 it is tried twice more (see Queue and settings) before the error is shown.
- **"Update and retry" does little for a queue of downloads.** An update can't be swapped in while other downloads are running (see Managed binaries), so when every video of a playlist fails for the same reason, each falls back to the ordinary retries.
- **HLS trimmed parts print many "keepalive request failed" warnings** from ffmpeg. They are harmless; the download works.
- **YouTube draws its own overlay on the paused preview.** With the official embedded player, a paused frame is partly covered by the video title, a play button and "More videos". The API offers no way to hide them. Scrubbing still shows the frame underneath.
- **The YouTube embed can stall in "buffering" after a seek.** `YouTubePlayer.tsx` nudges it out with a second seek.
- **The last-resort preview copy still covers the whole length.** When neither the embed nor a stream plays, `download_proxy` fetches the smallest picture near 360p (at most 480p, or the smallest the site has) with the smallest sound, and gives up above 500 MB rather than spend minutes on it. A window around the selected part would be lighter still, but the timeline needs the whole video to scrub.
- **A proxy setup script (PAC) is not followed**, by yt-dlp or by Siphon's proxy, nor is a proxy reached over TLS (`https://` in `HTTPS_PROXY`); with either, downloads reach the site directly.
- **Siphon is Windows only** (decided 2026-11-17). The macOS build had never been run, and an unsigned, un-notarised Mac app is blocked by macOS for most users, so the macOS bundle, its CI job and its release assets, the macOS tool downloads, the system-FFmpeg fallback and VideoToolbox were removed. This is about the platform Siphon runs on; the iPhone / iPad / Mac **preset** is unaffected.
- **The dev server can miss quick successive edits to a file** and go on serving an older version, even after a full reload (seen 2026-11-18: a half-edited `PlaylistPane.tsx` threw `changeOptions is not defined`). If the running app disagrees with the file on disk, check what `http://localhost:1420/src/<path>` serves, and re-save (`touch`) the file.
- **The dev server needs the project path spelled as Windows spells it.** Started from `c:\Repos\siphon` (lowercase, as some editors do), Vite bundled React twice and the dev window stayed blank with "Invalid hook call". `vite.config.ts` now sets `root` from `realpathSync.native`, which fixes it. If it ever comes back, delete `node_modules/.vite` and start again from `C:\`.
- **ESLint's TypeScript parser doesn't support TypeScript 7**, so the frontend is linted with oxlint (`npm run lint`, `.oxlintrc.json`): correctness rules, React hooks and unused code. The React Compiler-style rules (`set-state-in-effect`, `refs`) are off; they flag working patterns throughout the app. `npm run knip` finds unused files, exports and dependencies.
- **The shadcn CLI mis-resolves the `@/` alias.** It writes `import { cn } from "cn"` and installs a package called `cn`. After `npx shadcn add …`, change the import to `@/lib/utils` and run `npm uninstall cn`.
